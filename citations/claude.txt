  Root Cause

  The bug is in slam.cpp::sensor_callback (lines 138–143). Here's the problem:

  fake_sensor publishes obstacle positions as absolute world coordinates in 
  nusim/world frame (m.pose.position.x = x + noise where x is the obstacle's
  world X). That's verified in nusim.cpp:325–326.

  sensor_callback converts these to range/bearing by subtracting ekf_->pose()
  (the estimated robot position). This is wrong — the conversion from
  world-frame absolute position to robot-body-relative range/bearing requires
  the true robot position, not the EKF estimate.

  The result: both the actual measurement z and the predicted measurement z_hat
  end up using the same EKF robot position in their computation, so the
  innovation z - z_hat is always near-zero with respect to robot pose errors.
  The EKF update can never correct dead-reckoning drift — it only ever sees zero
   (or noise-level) innovations, and the odometry drift accumulates uncorrected.

  The Fix

  In nusim.cpp: makeNoisyCylinder already has dx = x - x_ / dy = y - y_
  (obstacle relative to the true robot). It just needs to rotate those into the
  robot body frame and publish them there, which is what a real range sensor
  would give.

  In slam.cpp: sensor_callback should then treat the marker positions as
  body-relative and compute r/phi directly, with no EKF pose subtraction.

● Both changes look correct. Here's a summary of what was found and fixed:

  ---
  What Was Wrong

  nusim.cpp::makeNoisyCylinder (lines 325–326, before fix) published obstacle
  positions as absolute world coordinates: x + noise, y + noise in frame_id = 
  "nusim/world".

  slam.cpp::sensor_callback (lines 138–143, before fix) tried to convert those
  absolute world positions to body-frame range/bearing by subtracting
  ekf_->pose() — the estimated robot position.

  This created a circular dependency that killed SLAM correction:
  - The "measurement" z used the EKF robot pose to compute range/bearing
  - The predicted measurement ẑ also uses the EKF robot pose (that's the whole
  measurement model)
  - So the innovation z − ẑ was always ~0 with respect to any robot pose error
  - Dead-reckoning drift accumulated with no correction, causing the green robot
   to float away

  For example, if the true robot drifted to x=1.0 but EKF still thought x=0.9,
  and a landmark sits at x=2.0:
  - True measurement: r = 1.0 (landmark 1m from true robot)
  - Code computed: r = 2.0 − 0.9 = 1.1 (using EKF position)
  - Predicted: r̂ = 2.0 − 0.9 = 1.1 (same EKF position)
  - Innovation: 0 → no correction

  What the Fix Does

  nusim.cpp: The world-relative offset (dx, dy) is now rotated into the true 
  robot body frame using theta_ (the ground-truth robot heading) before
  publishing. The frame_id is set to "red/base_footprint" to correctly describe
  what the values mean.

  slam.cpp: The body-frame marker position (mx, my) is used directly. Range is
  sqrt(mx²+my²) and bearing is atan2(my, mx) — the true sensor reading,
  independent of the EKF state. Now the innovation genuinely reflects robot pose
   errors and SLAM can correct them.
