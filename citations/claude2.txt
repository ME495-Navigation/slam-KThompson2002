❯ Ok, in the current state with no sensor noise the system works fine until it  
sees a 4th or 5th landmark, and at that point the green odometry spikes to a    
random location and begins publishing bad landmark locations as it is           
publishing landmarks relative to it's incorrect pose. What are some good ways   
to solve this                                                                   

● The spike at the 4th/5th landmark is almost certainly the Mahalanobis 
  degeneration problem caused by the large initial landmark covariance (1e6).

  Here's why it happens: when a new landmark is promoted with P_new = 1e6 on its
   diagonal, Ψ = H·P·H^T + R is dominated by that 1e6 term, making Ψ^{-1} ≈
  10^{-6}. The Mahalanobis distance d = dz^T · Ψ^{-1} · dz is then essentially
  zero for any measurement, regardless of how far away it actually is. So on the
   next scan, every landmark measurement associates with the newest
  (highest-uncertainty) landmark instead of the correct one. The resulting wrong
   update drives the robot state to a bad location.

  Good solutions, roughly in order of simplicity:

  1. Lower the initial landmark covariance (ekf.cpp, initialize_landmark_at and
  initialize_landmark)
  Change 1e6 to something reflecting actual positional uncertainty at
  initialization — e.g. 0.5 to 2.0. Since the provisional tracking already
  averages multiple TF-derived positions, the initial uncertainty is not
  "infinite." This is the most direct fix.
  2. Add a Euclidean pre-filter inside try_associate before computing
  Mahalanobis
  Back-project (r, phi) to map frame using the current EKF pose, then skip any
  landmark whose Euclidean distance to that projected point exceeds some
  threshold (e.g. 1.0 m). This prevents high-covariance landmarks from
  attracting distant measurements even if Mahalanobis fails.
  3. Warm-up period: skip newly added landmarks in try_associate
  Track a per-landmark settled flag or update count. Only include a landmark in
  Mahalanobis association after it has received, say, 3 updates (by which point
  P has converged and Ψ is well-conditioned).
  4. Don't call update immediately on promotion
  Currently when promoting a provisional, you call initialize_landmark_at then
  update in the same callback. Skipping the immediate update means the new
  landmark's first real association happens through try_associate on the next
  scan — but this doesn't fix the Mahalanobis problem so it must be paired with
  option 1 or 2.

  Recommended combination: options 1 + 2. Lower the initial covariance to
  something like 1.0 (or even compute it from the variance of the provisional
  observations), and add a Euclidean pre-filter as a safety guard. That makes
  the system robust even if the covariance estimate is imperfect.

  Look at lines 426-465 in timer_callback:

  wheel_pos.left  += left_wheel_vel * (1.0 + slip_dist()) * dt;  // slip applied
   here
  wheel_pos.right += right_wheel_vel * (1.0 + slip_dist()) * dt;

  msg.left_encoder = round(wheel_pos.left * encoder_ticks_per_rad);  // from 
  slipped wheel_pos
  joint_states.position = {wheel_pos.left, wheel_pos.right};          // from 
  slipped wheel_pos
  diff->forwardKinematics(wheel_pos);                                  // from 
  slipped wheel_pos → red TF

  The slip multiplier is applied to wheel_pos, and all three outputs —
  sensor_data, joint_states, and the actual robot pose TF — are computed from
  that same post-slip wheel_pos. So integrating the joint states via odometry
  exactly reproduces the actual robot motion. Blue = Red, always, regardless of
  slip fraction.

  The fix in nusim: Separate the encoder-reported position from the actual
  slipped position. In reality, encoders measure wheel rotation, not body
  translation — slip affects where the body ends up, but the encoder still
  counts the same wheel ticks:

  // Ideal wheel positions (what encoders measure — no slip awareness)
  wheel_pos.left  += left_wheel_vel * dt;
  wheel_pos.right += right_wheel_vel * dt;

  // Slipped positions for computing actual robot pose only
  turtlelib::Wheel slipped_pos;
  slipped_pos.left  = wheel_pos.left  + left_vel_for_tick  * slip_dist() * dt;
  slipped_pos.right = wheel_pos.right + right_vel_for_tick * slip_dist() * dt;

  sensor_data (encoders)  → from wheel_pos      (no slip)
  joint_states.position   → from wheel_pos      (no slip)
  forwardKinematics(...)  → from slipped_pos    (with slip) → drives red TF

  With that change, the launch file wiring is already correct: blue and green
  read red/joint_states (ideal, no slip), do odometry, and their dead-reckoning
  drifts away from the actual red/base_footprint over time — which is exactly
  the divergence you want to demonstrate.

● Several issues across both files:

  turtlebot_bringup.launch.xml

  1. Joint state topic mismatch (critical): turtle_control publishes
  blue/joint_states, but the slam and green odometry nodes on the PC subscribe
  to red/joint_states. Neither will receive wheel data. Either rename to
  red/joint_states here, or update the PC side to subscribe to
  blue/joint_states. Pick one convention and stick to it.
  2. Inline params instead of yaml: The odometry node sets track and radius
  inline rather than loading diff_params.yaml. The other nodes all use the yaml
  file — this should too for consistency and to avoid silent divergence if
  parameters change.

  pc_bringup.launch.xml

  3. exec="slam_data" (critical): The executable built by CMakeLists is slam,
  not slam_data. This node won't launch.
  4. body_id = "red/base_footprint" (critical): There's no red robot in the real
   setup. The turtlebot's odometry publishes odom → blue/base_footprint, so the
  slam node's body_id must be blue/base_footprint to match. With
  red/base_footprint the TF chain is broken.
  5. remap joint_states to="red/joint_states": Same mismatch as point 1 — the
  turtlebot is publishing blue/joint_states, so this remap target needs to
  match.
  6. Landmark node missing laser scan remap: In simulation, landmark subscribes
  to red/laser_scan. The hlds_laser_publisher on the real robot publishes to
  /scan. You need <remap from="laser_scan" to="/scan"/> (or whatever topic the
  driver publishes) in the landmark node.
  7. load_one for green robot is missing: Blue has a load_one, but green
  doesn't. The green odometry publishes the odom → green/base_footprint TF, but
  without the URDF loaded for green the robot model won't render in RViz.

❯ Any thoughts on how I can optimize my parameter for real lidar data           

● Key differences with real LiDAR that affect each parameter:

  min_cluster (currently 5) — lower this
  The HLS-LFCD has 1° angular resolution. A 0.038m cylinder at 1.5m range
  subtends ~2.9°, giving only 3 points. At 2m you get 2-3 points. min_cluster=5
  means you only detect cylinders reliably inside ~1m. Lower to 3.

  cluster_threshold (currently 0.1m) — this is fine
  At 2m range, adjacent scan points are 0.035m apart. 0.1m gives enough margin
  for a gap between a cylinder and a wall without merging them.

  min_radius/max_radius (0.02–0.07m) — widen the max slightly
  Real LiDAR noise makes the algebraic circle fit less precise than simulation —
   the fitted radius can run high, especially with only 3-4 points. Try
  0.01–0.09m.

  min_angle/max_angle (1.5–2.5) — this is where real data diverges most
  With only 3-4 points on a cylinder arc, the inscribed angle computation is
  much more sensitive to noise. The angle variance across points is larger, and
  the mean shifts depending on how much arc is visible. A wider window like
  1.0–3.0 is safer for real data, then tighten it once you see what your actual
  detections look like.

  Practical tuning workflow:
  1. Set loose parameters first (min_cluster=3, min_angle=1.0, max_angle=3.0,
  radius 0.01–0.09)
  2. Drive past a known cylinder and check /landmark/landmark_pub — verify you
  get a detection
  3. Check how many false positives you get from walls with those loose settings
  4. Tighten min_angle/max_angle and the radius filter until walls are rejected
  but cylinders still pass

  One other real-robot issue: the LiDAR's range_min (0.12m) means very close
  cylinders get no scan points at all — keep that in mind if detections drop at
  close range.
